# NEMT Micro-Task Protocol V1.0

> **强制开发原则：一次任务、一个目标、一个验证结果、一个 Git Commit。**
>
> 适用于 Codex、Claude Code、开发人员及其他 AI Agent。目标是降低任务变形、上下文失真、意外修改和回归风险。

## 1. 时间与范围

- 每个独立任务以 **15–30 分钟**为规划目标；这是预算而非完成保证。
- 一次只交付 **一个可验证的最小成果**，不能把多个独立功能捆绑成一次任务。
- 如果预估超过 30 分钟，**在开始前拆分**为多个有依赖关系的小任务。
- 如果执行期间发现范围变大，在安全断点停止：记录已完成部分、阻塞、后续拆分；不要为了赶时间降低质量。
- 发现不相关问题，只记录到 Backlog 或报告，不自动扩大本次任务。安全性阻断除外：先停止并报告。
- 默认不自动继续下一任务，待审核通过后再开始。

## 2. 任务开始前：最小契约

每个任务必须写明：

| 字段 | 要求 |
| --- | --- |
| Task ID | 稳定唯一编号，例如 `NEMT-001` |
| Objective | 用一句话描述唯一目标 |
| Context | 当前代码与相关模块的实际状态，引用路径/证据 |
| Timebox | 15–30 分钟规划窗口 |
| Allowed scope | 允许修改的目录/文件及理由 |
| Forbidden scope | 不得碰的模块、配置、密钥与环境 |
| Steps | 3–5 项明确实施步骤 |
| Tests | 与变更直接相关的验证命令和预期 |
| Acceptance | 可客观核查的完成条件 |
| Stop conditions | 超时、缺少权限、环境不一致、风险升级时停止的条件 |
| Deliverable | 文件、测试结果、Commit、简短报告 |

**先查现状，再执行。** 不得凭旧版文档假定某路径、框架、依赖或功能一定存在。遵循仓库 `AGENTS.md` 和方向锁；若文件缺失或规则冲突，报告并请求确认，不擅自忽略。

## 3. 执行纪律

1. 阅读本协议、仓库 `AGENTS.md`、相关方向锁及任务限定的代码。
2. 检查 `git status` 与当前分支，避免覆盖未提交的工作。
3. 仅实现任务目标要求的最小改动；优先复用已有接口。
4. 为每个行为变更新增/调整直接对应的测试；文档审计任务可注明无需运行测试。
5. 运行最小相关测试，再按风险决定是否需要扩大验证。
6. 审查 diff：不得夹带无关格式化、删除、依赖升级或重构。
7. 在当前允许的开发分支提交**一个逻辑上完整的 Commit**；若无法安全提交，记录原因而非强行提交。
8. 输出验收摘要并**停止**，不得擅自执行下一任务。

## 4. 硬性安全边界

- NEMT 默认 **PAPER / DEMO ONLY**。不因任务、测试、UI 或 Agent 行为自动启用 Binance 真实交易。
- 不泄露、不提交、不打印 API Secret、会话密钥或其他凭证。
- 不擅自修改 IAM、网络安全组、正式服务、生产数据库、真实资金或交易所权限。
- 触及交易风控、账户权限、数据迁移、生产部署的任务必须**独立拆分并单独审批**。
- 不伪造行情、策略表现、实验结果或测试结论。
- 不允许未验证策略自动进入真实执行。
- 若缺少访问权限、环境不一致、网络不可达或规则冲突，应报告阻塞，不自行绕过。

## 5. 最小任务模板

```markdown
# NEMT-XXX — 单一任务名称
- 预计耗时：15–30 分钟
- 目标：本次只完成……
- 当前依据：相关文件、接口或测试……
- 允许修改：……
- 禁止修改：……
- 实施步骤：
  1. …
  2. …
  3. …
- 验收标准：
  - [ ] …
  - [ ] …
- 测试命令：…
- 停止条件：超过预期范围、存在安全风险或缺少必要权限
- 交付：Commit SHA、变更摘要、测试结果、遗留问题
- 本任务完成后立即停止，不自动开始 NEMT-XXX+1
```

## 6. 每次交付必须报告

```text
Task ID:
Status: PASS / PARTIAL / BLOCKED / FAIL
Elapsed:
Files changed:
Test command and result:
Commit SHA / branch:
Scope deviations: none / details
Risks or blockers:
Proposed next micro-task: (只提议，不执行)
```

只报告真实执行结果；不要宣称未运行的测试通过。

## 7. 成功标准

成功不是修改文件越多越好，而是：

**目标清楚 → 修改受控 → 结果可测 → 提交可追溯 → 审核后继续。**

如单项功能仍过大，再拆小。长期以小步稳定前进，而非一次生成庞大系统。
