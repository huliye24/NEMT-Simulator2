## 验证任务 V-001：MarketState 七维度充分性验证

### 问题来源

ADV-0001 待验证问题 1：
> NEMT 的最小状态对象是否应包含 MacroTrend、Regime、Liquidity、RiskAppetite、Volatility、Momentum、DrawdownRisk？

### 验证方法

**步骤 1：维度覆盖检查**

对照宏观趋势调度学核心概念词典和研究纲领，检查 MarketState 的七个维度是否覆盖了全部理论概念：

```text
市场阶段层 ✓ → Regime
宏观变量层：
  流动性周期 ✓ → Liquidity
  美元周期   → 已合并入 MacroTrend（DollarPressureScore）
  利率预期   → 已合并入 MacroTrend（RateExpectationScore）
  风险偏好   ✓ → RiskAppetite
趋势识别层：
  趋势强度   → 已合并入 MacroTrend
  趋势确认   → 在 Regime 分类规则中体现
  趋势衰减   → 在 Momentum 变化中体现
  趋势反转   → REVERSAL_WATCH
  假突破     → 在 RegimeConfidence 中体现
  波动率     ✓ → Volatility
  动量       ✓ → Momentum
风险控制层：
  最大回撤   ✓ → DrawdownRisk
  仓位上限   → 在 RiskController 硬约束中
  再平衡     → 在 PositionScheduler 中
```

**步骤 2：冗余检查**

检查七个维度之间是否存在高相关性导致的信息冗余：

```text
| 维度对 | 潜在冗余风险 | 验证方式 |
| Liquidity vs. RiskAppetite | 流动性充裕通常伴随高风险偏好 | 计算相关系数，若 >0.8 且长期稳定，考虑合并 |
| MacroTrend vs. Momentum | 趋势评分可能包含动量信息 | 检查 MacroTrendScore 各子项是否已含价格动量 |
| Volatility vs. DrawdownRisk | 高波动通常伴随高回撤风险 | 它们是不同概念——波动率是分布特征，回撤风险是尾部风险 |
```

**步骤 3：遗漏检查**

识别是否有遗漏的关键维度：

```text
候选维度 1：NarrativeScore（叙事强度）
  → 当前在 MacroTrendEngine 中作为惩罚项存在
  → 是否应该独立为一个维度？

候选维度 2：CorrelationRegime（资产相关性结构）
  → 加密资产之间的相关性在 risk-on/risk-off 切换时剧烈变化
  → 是否应纳入 MarketState？
  → 初步判断：相关性变化是 Regime 切换的结果而非独立维度，暂不纳入

候选维度 3：LeverageCycle（杠杆周期）
  → 当前作为 LeverageRiskScore 在 MacroTrend 中作为惩罚项
  → 是否应独立为 MarketState 的一个维度？
  → 初步判断：杠杆是风险指标而非状态维度，归入 RiskController 更合适
```

### 所需数据

```text
1. BTC 日线 OHLCV（2015-至今）
2. 美元指数 DXY
3. 联邦基金利率
4. VIX
5. BTC ETF 资金流（2024-至今）
6. 稳定币总市值
7. BTC 链上数据（长期持有者供应比例、交易所余额）
8. 未平仓合约 + 资金费率
```

### 验收标准

```text
✓ 七个维度无冗余（两两相关系数 < 0.8）
✓ 七个维度覆盖核心概念词典全部层级
✓ 无遗漏的关键宏观/市场维度
✓ 每个维度有明确的更新频率定义
```

### 连接

```text
案例库：使用历史关键事件（2020.3 流动性危机、2021.4 Coinbase上市、2022.11 FTX、2024.1 ETF获批）
        验证 MarketState 在这些事件前后的变化是否合理
反证区：如果某个关键事件中 MarketState 未能捕捉到风险信号 → 记录反证
回测框架：对 MarketState 各维度的历史值进行统计分布分析
```

## 验证任务 V-002：回测与反证的边权重验证

### 问题来源

ADV-0001 待验证问题 2：
> 宏观趋势调度学的论文网络是否应把回测和反证作为最高权重边？

### 验证方法

**步骤 1：理论论证**

BRANCH-NETWORK-001 已给出初步论证：

```text
BacktestEdge 权重 × 2.0：回测提供最硬的经验验证
FalsificationEdge 权重 × 2.0：反证提供最关键的修正信号
其他四类边权重 × 1.0（SignalEdge × 0.8）
```

需要进一步论证的是：

```text
Q: 回测边权重是否应该根据回测质量动态调整？
A: 建议是。回测质量可以通过以下维度评估：
   - 样本外验证通过率
   - 回测覆盖的市场 Regime 种类数
   - 参数敏感性（参数小幅变化时回测结果是否稳定）

Q: 反证边的权重是否应该根据失效的严重程度分级？
A: 建议是。反证严重程度可分为：
   - Level 1：策略在特定 Regime 中表现不如基准
   - Level 2：策略在特定 Regime 中亏损
   - Level 3：策略在特定 Regime 中超过最大回撤限制
   - Level 4：策略的核心假设被市场证伪
```

**步骤 2：历史验证**

使用已知的市场历史检验边权重逻辑：

```text
测试案例 1：如果一个策略论文没有任何 BacktestEdge → 应被标记为"未验证"
测试案例 2：如果一个策略论文仅有回测边、无反证边 → 应被标记为"待反证审查"
测试案例 3：如果一个策略论文同时有回测边 + 反证边 + 修正记录 → 置信度最高

当前论文网络中有多少论文符合案例 3？
→ 目前几乎没有，因为反证区刚建立
→ 这是 ADV-0002 需要重点推进的方向
```

### 所需数据

```text
1. 论文网络当前的完整边列表（需从头标注所有隐式边）
2. 回测框架的输出格式定义（确保回测结果可被结构化引用）
3. 反证区的结构化模板（确保反证记录包含严重程度评级）
```

### 验收标准

```text
✓ 六类边的权重逻辑有清晰论证
✓ 回测边的权重分级机制已定义（基于回测质量）
✓ 反证边的严重程度分级已定义（Level 1-4）
✓ 论文网络中至少 3 条论文已显式标注 BacktestEdge
✓ 反证区中至少 2 条反证记录已显式标注 FalsificationEdge
```

### 连接

```text
案例库：选取 3-5 个历史案例验证边权重的合理性
反证区：建立反证记录的结构化模板（含严重程度字段）
回测框架：定义回测报告的标准化输出（以便生成 BacktestEdge）
```

## 验证任务 V-003：NEMT 初期资产范围验证

### 问题来源

ADV-0001 待验证问题 3：
> NEMT 初期应先做 BTC/ETH/稳定币三资产配置，还是扩展到美股、黄金、美元指数？

### 验证方法

**方案 A：BTC/ETH/稳定币（最小可行资产集）**

优势：
- 数据获取简单（全部在链上或加密数据源）
- 交易执行简单（不需要跨市场账户）
- 资产之间的相关性结构相对稳定
- 宏观趋势调度学的初始论文全部围绕加密资产

劣势：
- 在极端加密熊市中缺少对冲工具
- 无法直接表达"风险偏好从加密转向黄金"的判断
- 资产多样性不足

**方案 B：BTC/ETH/稳定币 + 黄金ETF + 美元指数ETF**

优势：
- 可以用黄金作为宏观避险工具
- 可以用美元指数多头作为美元走强的直接表达
- 资产之间的风险因子更加分散

劣势：
- 跨市场数据源增加系统复杂度
- 交易执行需要股票/ETF 账户（增加合规和操作复杂度）
- 初期研究成果主要覆盖加密资产，黄金和美元的研究论文尚未完成

**方案 C：方案 A + 观察但不交易方案 B 的资产**

优势：
- 保持执行简单
- 同时积累扩展资产的观察数据
- 为未来扩展留下准备

劣势：
- 观察数据不能直接用于回测（因为没有实际交易记录）

### 推荐

```text
初期（MVP）：方案 A（BTC/ETH/稳定币）
  - 理由：论文网络和回测框架均以此为基础
  - 28 篇已有论文全部围绕加密资产
  - 系统复杂度可控

中期（Phase 2）：方案 C（A + 观察扩展资产）
  - 新增研究论文：黄金与比特币在宏观避险中的功能差异
  - 新增研究论文：美元指数作为 NEMT 对冲资产的有效性
  - 数据采集但不交易

远期（Phase 3）：方案 B（全资产配置）
  - 在扩展资产论文群完成 + 回测验证后
  - 以新增 NEMT 模块的方式扩展（而非修改核心引擎）
```

### 所需数据

```text
方案 A 的数据已经在回测框架论文中列出
方案 B 额外需要：
  1. GLD（黄金ETF）价格
  2. UUP（美元指数ETF）价格
  3. QQQ（纳斯达克ETF）价格（作为风险偏好对比基准）
```

### 验收标准

```text
✓ 方案选择有明确论证（基于论文网络覆盖度和系统复杂度）
✓ 无论选择哪条路径，N01-N04 的架构不依赖资产数量
✓ 资产配置引擎（N03）的权重矩阵应支持资产集的动态扩展
```

### 连接

```text
案例库：如果选择方案 A，需要在案例库中记录"纯加密组合在市场崩盘中的回撤"
反证区：如果方案 A 在极端行情中失效，触发扩展资产的讨论
回测框架：回测引擎（N05）应设计为资产无关的，支持任意资产集的回测
```

## 验证任务 V-004：公式化的必要环节识别

### 问题来源

ADV-0001 待验证问题 4：
> 宏观判断到自动调仓之间，哪些环节必须公式化？

### 验证方法

**环节清单与公式化判断：**

```text
| 环节 | 是否必须公式化 | 理由 | 公式化程度 |
| 宏观数据采集 | 否（配置化） | 数据源和采集频率应可配置，不需要公式 | 配置文件（YAML） |
| 宏观趋势评分 | **是** | 主观判断无法复现，必须公式化 | FORM-001 第三节 |
| 市场状态分类 | **是** | 分类规则必须是确定性的，否则回测无意义 | FORM-001 第四节 |
| 仓位目标生成 | **是** | 权重必须是计算出来的，不能靠感觉 | FORM-001 第五节 |
| 风险约束检查 | **是** | 硬约束必须是精确的数值边界 | FORM-001 第六节 |
| 再平衡触发 | **是** | 触发条件必须是可编程的规则 | 阈值公式 |
| 调仓执行 | 否（工程化） | 执行质量取决于 API/流动性/滑点控制，属于工程问题 | 工程配置 |
| 绩效评估 | **是** | 评估公式必须统一，否则无法跨周期比较 | FORM-001 第七节 |
| 复盘与修正建议 | 部分公式化 | 绩效归因可以公式化，但修正建议需要人工判断 | 半公式化 |
```

### 关键发现

并不是所有环节都必须公式化。必须区分三类环节：

```text
第 1 类：必须公式化（决定系统行为的核心逻辑）
  → MacroTrendScore、Regime 分类、权重生成、风险约束、绩效评估

第 2 类：配置化即可（参数而非公式）
  → 数据源选择、更新频率、资产列表、回测参数

第 3 类：保持人工判断（公式化会降低灵活性）
  → 修正建议生成、策略方向调整、新因子引入决策
```

### 所需数据

```text
无额外数据需求——这是方法论层面判断
```

### 验收标准

```text
✓ 每个环节的公式化/配置化/人工判断分类有明确理由
✓ 第 1 类环节在 FORM-001 中有对应公式
✓ 第 2 类环节在 NEMT 代码中有对应配置文件
✓ 第 3 类环节有明确的人工审查流程
```

### 连接

```text
案例库：不直接关联
反证区：如果某个被判定为"可公式化"的环节在实际运行中频繁需要人工干预
        → 反证该判断 → 重新评估其公式化程度
回测框架：第 1 类环节的公式需要在回测中验证稳定性
```
